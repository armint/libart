# Agent Instructions for libArT

## Purpose

`libArT` is a core utility library designed for embedded systems, providing abstractions for common tasks. Target
systems are cortex-m or risc-v microcontrollers running bare-metal or rtos-based (freertos or µOS++ IIIe).

## Core Components
- **Streams**: `Readable` and `Writable` interfaces for various data sources/sinks (Array, String, Digest, etc.).
  `FileReadable` and `FileWritable` (`src/streams/`) adapt an `art::storage::File` of any `FileSystem` to these interfaces, so `DigestReadable`, `BufferedWritable` and the codecs work on a file whatever its file system. `FileReadable` takes a caller-provided read buffer; `FileWritable` is unbuffered (wrap it in `BufferedWritable`) and reports `data.size()` on success because `File::write()` is all-or-error. `art::storage::Error` is mapped onto the existing `Readable::Error`/`Writable::Error` values (see the class comments) and the cause stays available in `lastError()`. `FatFileReadable`/`FatFileWritable` remain for `FatFile`.
- **Logging**: A flexible logging system (`LogManager`, `Logger`).
- **Modbus**: Implementations for Modbus Master and Slave.
- **Settings**: A framework for managing device settings.
- **Storage**: `art::storage` block device (`BlockDevice`) and file system (`FileSystem`, move-only `File` handle) interfaces; the FileSystem serializes its own calls, a BlockDevice does not. `LittleFsFileSystem` (`src/storage/littlefs/`) is the LittleFS implementation. It is built by the optional `art-storage-littlefs` target (`ART_STORAGE_LITTLEFS`, off by default) and is excluded from `art-core`, so `art-core` needs no littlefs. littlefs is pinned to v2.11.3 there, by commit: a tarball of that commit with its SHA256 hash (`URL`, `URL_HASH`), unless the superproject already defines a `littlefs` target, which then owns the pin. The binding reads littlefs internals, so `LittleFsFileSystem.cpp` refuses to compile against anything but the reviewed minor versions v2.9 and v2.11 (`static_assert` on `LFS_VERSION`; v2.10 was not reviewed). Against v2.9.3 the two trailing-slash tests are left out, because that version accepts a slash after a file. The on-disk format is the same in both (`tests/storage/TestLittleFsCompat.cpp` mounts a volume image written by v2.9.3). A failed `rename()` (any rename: whether it commits twice depends on the metadata pair, not on the directory), a failed `makeConsistent()` or a failed change while another file is open for writing poisons the mount: every call fails with `Error::NeedsRemount` until `unmount()` (which commits nothing and drops the unsynced data of open writers) and `mount()` (see "Poisoned mount" in `LittleFsFileSystem.h`, `tests/storage/TestLittleFsPoison.cpp`). After such a remount, or after an unclean power-down, `visitDirectory()` misses the entry that follows the moved one in the directory a rename moved from, and `stat()`, `open()` for reading and `readFile()` report `NoEntry` for it, until the first change of the volume (littlefs applies the pending move only in its first mutating call; an upstream regression, littlefs commit ddbfcaa7 in v2.9.1 to v2.11.3). The application must call `makeConsistent()` (wraps `lfs_fs_mkconsistent()`) after `mount()` and before it lists or stats anything that matters, in practice once per boot, and if it fails (it poisons the mount) remount and go on read-only without it instead of retrying in a loop: it is not part of `mount()`, because a mount that writes can fail on the failing medium that needs the repair; it reads and writes nothing on a consistent volume; and a failure of it poisons the mount (see "Consistency after a remount" in `LittleFsFileSystem.h`, `tests/storage/TestLittleFsConsistency.cpp`). Any new mutating call must report its failure through `failedMutation()`, and any new public method or file hook must start with the `refusal()` / `poisoned_` check. Move the pin in its own change, review the binding against `lfs.c` (`dropReadCaches()`, `resetProgramCache()`), extend the version check, add the image of the version you leave, and re-evaluate when a new 2.x release appears; v3 changes the on-disk format and is out of scope.
  `FatFileSystem` (FatFs, `src/storage/`) runs on a `BlockDevice` as well: its constructor takes a `BlockDevice &`, and `diskio.cpp`, the only place that knows the FAT sector size (`FF_MIN_SS`, 512 B), converts the sector numbers of FatFs into byte offsets. There is no other storage-device interface; the sector-based `StorageDevice` was removed (see the migration note below).
- **USB**: `src/usb/` (namespace `art::usb`) is a platform-independent USB full-speed device stack: `Device` (chapter 9 state machine, standard requests, EP0 control transfers with ZLP handling) on the packet-level `DeviceController` interface, and `Function` as the base of USB functions. `DescriptorBuilder.h` has the `constexpr` descriptor builders and the run-time `SerialNumber` string. No hardware code: a port (for example libart-stm32) implements `DeviceController`. Host tests use `tests/usb/FakeDeviceController.h`. See "USB device stack" in `README.md`.
- **Utils**: JSON reading/writing, CRC (Digest), string utilities, `FloatText` (`src/utils/FloatText.h`/`.cpp`, see "Dependencies" below) for portable float-to-text and text-to-float conversion, and more.
  The compat headers in `src/utils/compat/` (`art::expected`, `art::unexpected`, `art::span`, `art::bit_cast`, `art::is_little_endian`, `art::remove_cvref_t`) let code compile at C++17 and C++23. `art::expected`/`art::span` are the `std` types or libArT's own `expected` and `etl::span`, selected once per build by the CMake option `ART_USE_STD_EXPECTED_SPAN`, which art-core exports as a PUBLIC compile definition; never define it per translation unit (Readable/Writable have virtual functions with these types, so mixing is an ODR violation). See `README.md` and `utils/compat/config.h`.

## Migrating a `StorageDevice` implementation to `BlockDevice`

The sector-based `StorageDevice` interface no longer exists. A driver that implemented it (for example an SD card
over SPI) implements `art::storage::BlockDevice` (`src/storage/BlockDevice.h`) instead. All positions are byte
offsets, and results are `art::expected<void, Error>` instead of status flags and sector counts.

| `StorageDevice` | `BlockDevice` |
|---|---|
| `initialize()` returning status flags, `getStatus()` | `init()`. `FatFileSystem` remembers the outcome: a successful `init()` is "ready", a failure is `STA_NOINIT`. Return `Error::NotReady` for an empty slot. |
| `read(buffer, sector, count)`, returns the sector count | `read(sector * 512, span)`, returns `expected`. |
| `write(buffer, sector, count)` | `program(sector * 512, span)`. An SD card sets `eraseBeforeProgram = false`. |
| `getSectorCount()`, `getBlockSize()` | `geometry().size` (bytes) and `readSize`/`programSize` (512, or a divisor of 512). |
| `getEraseSize()` | `geometry().eraseSize`. An SD card reports 0 (its erase unit does not divide the capacity). |
| `erase(start, count)` | `erase(offset, length)`. With `eraseSize == 0` it succeeds and changes nothing. |
| nothing (FatFs `CTRL_SYNC` was a no-op) | `sync()`. `FatFileSystem` calls it for `CTRL_SYNC`; override it if the driver buffers writes. |

Behaviour to know when porting:

- `FatFileSystem` refuses a device (`FR_NOT_READY` on mount or format) whose geometry fails `Geometry::isValid()`,
  whose `readSize` or `programSize` does not divide 512, or whose capacity is below one sector or above 2^32 - 1
  sectors.
- `diskio.cpp` maps `Error::NotReady` and `Error::NotInitialised` to `RES_NOTRDY`, `WriteProtected` to `RES_WRPRT`,
  `InvalidArgument` to `RES_PARERR` and every other error to `RES_ERROR`. After `NotReady` or `NotInitialised` the
  drive is not ready until `init()` succeeds again, which the next `f_mount()` does. This replaces a driver
  updating its own `STA_NOINIT` flag when a card is removed.
- A `BlockDevice` is not thread-safe. Serialize access to a device that is shared with anything other than FatFs.

## Guidelines

- **Language**: C++17 (or newer). Every library source and header must compile at C++17 (CI builds at C++17, C++20 and C++23; see `README.md`, "Requirements"); use the compat headers in `src/utils/compat/` for C++20/23 vocabulary types. Tests may use C++20 if `tests/CMakeLists.txt` leaves them out of the C++17 build. Use modern C++ features and best practices as long as they don't interfere with the embedded nature of the project (e.g., const correctness, move semantics, no c-style casts).
- **Style & Linting**: Follow the established stream patterns mechanically when adding new data handling utilities. Before completing tasks, format code using the provided CMake target: `cmake --build <build_dir> --target clangformat` (or `git clang-format-20 origin/dev` for only the lines you changed). Use clang-format 20, the version CI uses; other major versions format differently. `clangformat-check` changes nothing and fails if a file is not formatted; the CI job `format` runs it. Both targets cover `src/` and `tests/` and exist only when clang-format 18 or later is found and libArT is the top-level project (see "Formatting" in `README.md` and `cmake/clang-format.cmake`). Third-party sources (FatFs, `lists`) are listed in `.clang-format-ignore` and are never formatted. A commit that only reformats code gets its full SHA in `.git-blame-ignore-revs`.
- **Resource Management**: Use RAII for all resource management. Use `Writable` streams for formatted output in a memory-efficient way. Prefer `std::span` (or equivalent) for passing buffers to avoid size/pointer mismatches.
- **Memory**: Heap memory usage is strictly prohibited. Ensure that changes are compatible with the embedded nature of the project (low memory footprint).
- **Dependencies**: The `embedded template library` (ETL) is a PUBLIC dependency of art-core (`utils/compat/span.h` aliases `etl::span`) and should be considered before creating similar classes. `ETL_NO_STL` is not supported. Use etl classes for memory-efficient containers and algorithms. `FloatText` (`src/utils/`) is backed by [Ryu](https://github.com/ulfjack/ryu) for correctly-rounded, shortest-round-trip float-to-text and text-to-float conversion, with no newlib `printf`/`strtod`, no libm and no heap. Ryu is dual-licensed Apache-2.0 / Boost Software License 1.0 (BSL-1.0); **libArT uses it under BSL-1.0**, which needs no attribution in a distributed firmware binary (Apache-2.0 would bring NOTICE obligations). Ryu is fetched via CMake `FetchContent` from a pinned tarball + `URL_HASH` (not vendored, not a submodule; see `cmake/ryu.cmake`, included from the top-level `CMakeLists.txt` and `tests/CMakeLists.txt`) and populated only, never `add_subdirectory()`d: `src/utils/ryu_float.c` includes just the two float-only `.c` files (`f2s.c`, `s2f.c`) it needs, with `RYU_FLOAT_FULL_TABLE` selecting Ryu's small float-only tables instead of its larger double-derived ones, and forces `NDEBUG` for that translation unit regardless of the containing build's own build type so Ryu's internal `assert()` calls never pull in newlib's `printf`/`malloc` chain (define `LIBART_RYU_KEEP_ASSERTS` to opt back into them for local debugging). To build offline, or against a different checkout, point `FETCHCONTENT_SOURCE_DIR_RYU` at a local copy of the Ryu source tree instead of letting CMake download the tarball.
- **Conventions**: Always use meaningful and descriptive function and variable names that reflect their purpose. Use fixed-size integer types (`uint8_t`, `uint32_t`, etc.) for performance, memory efficiency, and portability. Document any new functions or changes with clear comments. Use comments to explain complex logic or non-obvious decisions.
